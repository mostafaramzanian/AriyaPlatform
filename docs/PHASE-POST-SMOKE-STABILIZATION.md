# Phase: Post-Smoke Stabilization & Runtime Drift Guards

## 1. Scope

This phase turns the two runtime defects discovered in **Phase: Live Runtime & E2E Smoke Verification** into repeatable, early-failing guards.

In-scope:

- Prisma schema ↔ migration history consistency (enums first, because that was the actual failure mode)
- Generated Prisma client freshness relative to the schema
- Runtime policy projection consistency
- Docker runtime artifact completeness for every implemented runtime image
- CI integration for the new gates
- Full regression and runtime re-verification

Out-of-scope (deliberately):

- New business behavior
- Financial / Production / Commerce workflow changes
- Standalone runtimes
- Browser E2E harness
- Notification queue runtime harness
- Load testing
- Registration/tenant onboarding behavior changes

## 3. Drift classes identified

From Phase Live Runtime:

| ID | Drift | Symptom | Root cause |
|----|-------|---------|------------|
| D1 | Prisma enum drift | `Value 'FINANCIAL' not found in enum 'PermissionDomain'` | Migration added `FINANCIAL`, schema omitted it, generated client therefore rejected the value |
| D2 | Docker artifact drift | `db:migrate` failed inside container with missing Observability schema | `Dockerfile.backend` did not COPY `apps/api/prisma/observability` |

These two classes are now guarded independently so they fail in CI before reaching a running container.

## 4. Guard A — Prisma schema / migration enum drift

### What it does

For every **implemented** datasource owner, the guard:

1. Parses enum declarations from `schema.prisma`.
2. Reconstructs the effective database enum state from the migration history:
   - `CREATE TYPE "EnumName" AS ENUM (...)` baseline
   - `ALTER TYPE "EnumName" ADD VALUE ...` additions in migration order
3. Compares the two sets and reports any difference.

### Implementation

- `apps/api/src/prisma-drift-guard.spec.ts`

### Failure injection evidence

Trigger: temporarily removed `FINANCIAL` from `PermissionDomain` in `apps/api/prisma/core/schema.prisma`.

```text
Prisma enum drift guard › owner: core › schema enum declarations match the effective migration history
  × FAIL
  PermissionDomain: schema=[..., PRODUCTION] migrations=[..., FINANCIAL] diff=[FINANCIAL]

Prisma enum drift guard › owner: core › generated Prisma client enum objects match the schema
  × FAIL
  PermissionDomain: schema=[..., PRODUCTION] generated=[..., FINANCIAL] diff=[FINANCIAL]
```

After restoring `FINANCIAL`:

```text
Test Suites: 1 passed, 1 total
Tests:       17 passed, 17 total
```

## 5. Guard B — Generated Prisma client freshness

### What it does

The same spec also parses enum objects from the generated Prisma client (`src/generated/<owner>-client/index.js`) and asserts they match the schema declarations.

This catches the stale-client half of the D1 failure: a developer updates the schema, runs tests, but forgets to regenerate the client.

### Implementation

Shared with Guard A in `apps/api/src/prisma-drift-guard.spec.ts`.

### Failure injection evidence

When `FINANCIAL` was removed from the schema while the generated client still contained it, the generated-client test failed with the diff shown above. After `prisma generate`, the generated client again matched the schema and the test passed.

## 6. Guard C — Runtime policy drift

### What it does

`apps/api/src/runtime-policy.spec.ts` already enforces that:

- `runtime-policy.json` equals the projection of `runtime-datasources.ts`
- Dockerfiles derive prune lists from the projection (no hand-maintained `rm -rf` lists)
- Health modules import exactly the instantiated datasources
- Unknown runtimes fail loudly instead of silently pruning nothing

No new code was required; this phase only re-verified the existing guard.

## 7. Guard D — Docker runtime artifact completeness

### What it does

For every runtime that has a Dockerfile (`core`, `cms`, `combined`), the guard:

1. Reads `COPY --from=builder /app/apps/api/prisma/<owner> ...` directives.
2. Computes the expected set from the canonical runtime policy:
   - `core` image: required datasource owners only → `core`
   - `cms` image: required datasource owners → `core`, `cms`
   - `combined` image: every implemented Prisma project, because this image hosts the all-owner `db:migrate` orchestration
3. Fails if any expected project is missing.

### Implementation

- `apps/api/src/docker-artifact-guard.spec.ts`

### Failure injection evidence

Trigger: temporarily removed the `prisma/observability` COPY line from `infrastructure/docker/Dockerfile.backend`.

```text
Docker runtime artifact completeness › combined Dockerfile copies exactly the expected Prisma projects
  × FAIL
  expected copied to contain "observability", received: ["commerce", "core", ..., "production"]
```

After restoring the COPY line:

```text

```

## 14. Known limitations

- The enum guard is text-based over `schema.prisma` and `migration.sql`; it does not replace a full Prisma migration diff against a live database. It is intentionally focused on the failure mode that actually broke runtime (enum member drift).
- The generated-client guard checks enum objects only. A full stale-client check can be added later via the embedded `prismaSchemaHash` if the team decides generated clients should be checked in.
- The Docker artifact guard checks `prisma/<owner>` COPY presence, not the generated-client tree directly, because client pruning is already enforced by `runtime-policy.spec.ts`.
- `observabilityDatabase` remains optional and degraded in the combined runtime; this is expected and unchanged.
- CI still does not run Docker E2E (documented as GAP-ENV-1).

## 15. Deferred items

- Full schema-level diff against a shadow database (requires a live or containerized PostgreSQL shadow DB).
- Generated-client hash-based freshness check.
- Runtime artifact completeness check for not-yet-implemented runtimes (e.g., `future-hr` has no Dockerfile).
- Browser / UI E2E drift guards.
- Load / concurrency drift detection.

## 16. Final verdict

**PASS**

Both runtime drift classes discovered in the previous phase now have executable, repeatable guards. The guards were proven to fail when the defects are reintroduced and pass on the restored, correct state. Full regression and runtime smoke remain green. No business behavior was changed.
